# 阶段② 迁移台账 —— JS → Java

> 目标：把 18 个 GraalJS 脚本逐个改成 Java，最终删掉 `lib/`（15 个 jar / 70.8 MB）
> 与整个 `script/host/` 包，插件只剩自己的代码。
>
> 台账的唯一事实来源是 `com.qinghuacisj.gs.script.Modules` 的静态登记块 ——
> 本文只是它的可读版本，**改代码时以 `Modules.java` 为准**。

## 迁移机制（增量、可回退）

`Script.of(name)` 是双路门面：

| 情况 | 走向 |
| --- | --- |
| `Modules.has(name)` == true | 走 Java 模块，**完全不碰 GraalJS** |
| 否则 | 回落 `Scripts`（内嵌 GraalJS 宿主） |

所以转好一个脚本 = **在 `Modules` 里加一行登记** + 写一个模块类，
其余代码（物品加载器、物品组按钮、事件监听器）零改动。

两条路都保持原版的**急切求值 + 按名缓存**语义：
`Modules.acquire` 用 `computeIfAbsent`，**模块的构造器 = 原脚本的顶层代码**，
**模块的成员字段 = 原脚本的顶层变量**。

### 加载期 vs 点击期（重要）

`items.yml` 的 `script:` 在**加载期**解析 ⇒ 模块在 onEnable 时就实例化。
`groups.yml` 的按钮 `actions: ["script X"]` 在**点击期**才解析
（`GsItemGroup.readAction` 里才 `Script.of`）⇒ 模块要到第一次点击才实例化。

所以启动日志的「本次实际实例化 N 个」**小于**「已 Java 化」是正常的。
当前实测：10 个已转，加载期实例化 7 个
（`gs_rolling_log_ingot` / `gs_ding_me` / `gs_song` / `gs_release_dream` / `gs_fake_weisi`
/ `gs_maiyou_wine` / `gs_borrow_life`），
另 3 个（`gs_info_creator` / `gs_update_log` / `gs_guide_book`）都是按钮专属。
这一点与原版 RSC 完全一致（它的按钮动作同样在点击时才 `getScriptOrNull`）。


## 转换纪律

1. **数值/概率/颜色码/tick 延迟逐字保留**，禁止「顺手优化」。
2. **JS 里有 `try/catch` 的必须保留 `try/catch`** —— 静默吞掉 vs 记一条日志
   是**可观察差异**，会改变现网日志。
3. **JS 里没有 `try/catch` 的就让它抛** —— 外层 `Script.call` 会吞掉并记日志，
   这正是原版 `evalFunction` 的行为。
4. **JS 浮点除法 vs Java 整数除法**是头号陷阱（已抓到一次）。
5. **JS 动态派发 vs Java 静态类型**：`addPotionEffect` 在 `LivingEntity` 上而不是
   `Entity` 上，必须显式转型（已抓到一次）。
6. 每转一个脚本，**同步更新 `Modules.java` 与本文**。

### 去抖必须「只查、不武装」

`gs_borrow_life` 的 150ms 去抖（一次右键会连发主手/副手两个事件）有个坑：
**不能每次按下都刷新去抖窗口** —— 冷却期间被挡掉的连点会把窗口一直往后推，
导致「冷却刚好结束的那一下」被误吞。原脚本注释里记着实例：
0/100/300/450/510 ms 连点，**510ms 那一下本该打出去**。

正确拆成两步：`isDuplicate()` **只读**，只有「这次真的生效」时才 `armDebounce()`。
`BorrowLifeParityProbe` 的 `[D]` 段用真时间把这条时序钉住了 ——
包括一条**反证**（故意用错法跑，确认它确实会吞掉 510ms 那一下）。

### 旋转判定盒的验证套路

`gs_borrow_life` 的判定体是**三维旋转**的（沿准星展开），这类几何最容易「抄错一点点、
表现为偶尔打不中」。套路是：
①把算式抽成静态方法（`basis()` / `inside()`），**抽出来不改行为**；
②用真 JS 跑同一算式，在**全角度 × 全位移**上逐值比对布尔结果（本轮 89.1 万组全等）；
③单独钉住「平视退化口径」——旋转版在 pitch=0 时必须与旧版逐点等价；
④搜索盒半径按**外接球**算（√(半长²+半宽²+半高²)），
   用「枚举判定盒 8 个角点、确认旧公式会漏搜」来证明这个修正不是多余的。

> ★ 边界网格点要跳过：扫描网格会**正好**落在 ±2.5 / ±1.0 上，
> 反投影回来可能是 `-2.5000000000000004` ⇒ `inside()` 正确地判为出界。
> 这是浮点边界、不是逻辑差异，按 1e-9 邻域跳过并统计跳过数。

## 配置读取类脚本的验证套路

配置里的钳制条件（`step < 0.1`、`hits` 夹到 1..10、`soundPitch` 夹到 0.5..2.0…）
**在正常配置里一条都不触发** —— 写错了平时看不出来，改了配置才炸。
所以验证必须两步：①真配置逐字段对账；②用极端值把每条钳制都踩一遍。
`ConfigParityProbe` 就是这个套路，照着抄。

### 长文案不要手抄

`gs_guide_book` 那 19 页是**玩家可见内容**，最长一页 173 字、含生僻符号。
做法是**从 JS 机械提取生成 Java 字面量**（按 JS 字符串转义规则反转义，再转 Java 字面量），
然后用 `GuideBookParityProbe` 做第二道独立校验。以后遇到长文案照这个流程走。

## ★★ 「`gs_xxx 已加载`」这一行不是框架统一打的

**踩过的坑**：给 5 个 boss 脚本写移植契约时，我想当然地给每个都列了
`[构思技艺] gs_boss_xxx 已加载`，结果 `gs_boss_nightwatch` 和 `gs_boss_shadow`
**压根没写这行日志**（全文搜 `已加载` 零命中）。

实测结论：这行是**脚本自己**打的，有的脚本有、有的没有。

| 有 | 没有 |
| --- | --- |
| `gs_release_dream` / `gs_fake_weisi` / `gs_maiyou_wine` / `gs_ding_me` / `gs_song` / `gs_guide_book` / `gs_boss_phantom` / `gs_boss_rider` / `gs_boss_three` / `gs_cursed` / `gs_bad_apple` | `gs_boss_nightwatch` / `gs_boss_shadow` |

**规则**：以**脚本文件本身**为准，以 `docs/参考服日志_构思技艺.txt` 为证。
脚本里没有 ⇒ Java 里也**不许有**（多打一条就是比真 JS 多一个可观察行为）。
并且探针里要加**反向断言**钉住「本模块的加载日志集合恰好等于参考服日志里那 N 行」，
这样日后有人「顺手补一行」会被测试拦住。

> ★ 教训：**凡是「预期行为」清单，都要回到源文件核一遍再采信**，
> 包括别人（或自己）写好的任务描述。

## ★★ Java 类文件的两个硬限制（10 万个 int 的教训）

`gs_bad_apple` 的 `SG_TL` 是 **109,386 个 int**（36,462 个音符 × 3）。
写成单个数组初始化器直接炸：

```
error: code too large
error: too many constants
```

**解法**：拆成 19 个静态方法 `t0()`…`t18()`（每个 6,000 个 int），
再用一个 `cat()` 做 `System.arraycopy` 拼起来。实测通过
（class 844,150 B，输出正确）。

**通用规则**：单个方法体超过 ~64KB 字节码、或单个类的常量池超过 65,535 项就会炸。
以后遇到大数组/大字符串表，**先拆块再拼**，别指望编译器。

## ★★ `gs_listener`（14,337 行）的拆分策略

它是**一个** JS 全局作用域，塞了 **24 个子系统**，不能当成一个类写。
做法：

1. **先机械普查共享面**：算「哪些顶层函数被 2 个以上子系统引用」⇒ 得到 **47 个**。
   再算「哪些顶层 var 跨子系统」⇒ 得到共享状态清单。
2. **抽 `ListenerCore`**：47 个共享函数 + 全部共享状态 + 共享 PDC 键 + 共享配置载体。
   ★ 跨子系统的耦合点（如 `WL_RIDE_TAG` 记分板标签 —— 五骊矟打标签、
   梦境套伤害拦截器读它）也要放这里。
3. **每个子系统一个类**，构造函数收 `ListenerCore`；只属于自己的顶层 var 做**实例字段**。
4. **启动顺序集中在一个表里**（`ListenerSubsystems.startAll`）。
   ★ 顺序是**可观察行为**：日志行的先后、同优先级监听器谁先收到事件、谁先占住共享资源。
   ★ 陷阱：原脚本「函数定义在前、顶层调用集中在中后段」，
   所以某子系统的**定义**可能在另一子系统的**调用点之后**
   （`gsEntPurge*` 定义在 11708，调用在 13569）—— 顺序表用**顶层调用**的行号。
5. **监听器注册改为幂等**：原脚本用 `pm.registerEvent(...)` 自己注册，
   **每次 reload 都再注册一遍、不断累积**（`GS_XX_REGISTERED` 闩锁挡不住，
   因为闩锁本身是脚本级变量、reload 后归零）。Java 侧写成 `Listener` 实现类 +
   `registerEvents` 注册一次 —— 可观察行为相同但不再累积。
   ★ 唯一必须保留的闩锁是 `GS_DA_REGISTERED`：它被兜底诊断**读**来改变行为。

### 已拆完的子块（各写各的类，互不引用）

| 类 | 覆盖脚本行 | 顶层入口（调用行） | 探针 |
| --- | --- | --- | --- |
| `listener/VoSub.java` | 7791~8599 | `gsVoStart()`（8599） | `tools/ListenerESubParityProbe.java` |
| `listener/SiSub.java` | 8601~9279 | `gsSiStart()`（9279） | 同上 |
| `listener/EmSub.java` | 9281~10837 | `gsEmStart()`（10837） | 同上 |
| `listener/WpnNoMeleeSub.java` | 10839~10950 | `gsWpnNoMeleeStart()`（10950） | 同上 |

四个类一次编译、一次对账，探针 `通过 392 ｜ 失败 0`（`build\sub_e` / `build\sub_e_probe`）。
探针里两条**必须记住的坑**（都是「Java 侧取真实时钟、JS 侧冻结时钟」造成的假红）：

1. **别把刀口值放进 JS↔Java 共用的网格里**。`gsEmPulse` / `gsXxSwing` 在 Java 里
   会**自己再取一次** `System.currentTimeMillis()`，而探针 JS 的 `__now` 是冻结的。
   网格点取 `319ms`（冷却 320）这类刀口时，Java 侧会漂到 320 ⇒ 偶发翻车。
   做法：**刀口单独钉真 JS**，网格只用离刀口 ≥ 100ms 的值。
2. **`Class.forName(String)` 会触发静态初始化**（等价于 `forName(name, true, cl)`）。
   探针要在 standalone 里撑起 `org.bukkit.Registry`，就必须先
   `Class.forName("org.bukkit.Registry", false, cl)` 只加载、把假
   `RegistryAccessHolder.INSTANCE`（`static final Optional`，只能走 `Unsafe`）塞进去，
   再让 `Registry` 自己 `<clinit>`。否则 `Material.isSolid()` 一路炸到
   `IllegalStateException: No RegistryAccess implementation found`。

## ★ 5 个 boss 脚本的脚手架普查（结论：只共 1 个函数）

机械比对（按各自前缀归一化后逐字节比函数体）：
5 个脚本共有 14 个**同名**函数，但**归一化后逐字节相同的只有 `IsMainHandUse` 一个**。
其余（`ApplyHp` / `HpDiag` / `BarMake` / `BarSync` / `SpawnMob` / `RefOf` …）
**数值与判定条件各不相同** ⇒ **不能抽公共代码**，只能各写各的。

> ★ 教训：**「看起来一样」不等于「一样」**。共享代码必须靠**逐字节比对**证明，
> 不能靠函数名相同来推断。这跟 `isMainHandUse` 在 10 个脚本里逐字相同是两回事。
